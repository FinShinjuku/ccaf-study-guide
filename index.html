1.1 自律タスク実行のためのエージェントループ

エージェントループは、Claude にリクエスト送信 → stop_reason 検査 → ツール実行 → 結果を会話履歴に追加 → 次のイテレーションという基本ライフサイクルで動きます。 モデルがコンテキストに基づき次に呼ぶツールを自律的に推論するのが本質です。

FIG 1.1.a エージェントループの制御フロー（stop_reason 分岐） 
stateDiagram-v2
  [*] --> SendRequest
  SendRequest: ユーザー入力 + 履歴を送信
  SendRequest --> InspectStop
  InspectStop: stop_reason を検査
  InspectStop --> RunTool: tool_use
  InspectStop --> [*]: end_turn
  RunTool: 要求されたツール実行
  RunTool --> AppendResult
  AppendResult: 結果を履歴に追加
  AppendResult --> SendRequest
知識
  • ライフサイクル: 送信 → stop_reason 検査 → 実行 → 履歴追加
  • ツール結果を会話履歴に追加 → 次の推論に組み込まれる
  • モデル駆動の意思決定 vs 事前設定の決定木
スキル
  • tool_use で続行、end_turn で終了の制御実装
  • イテレーション間でコンテキストにツール結果を追加
  • アンチパターン回避（自然言語シグナル解析、任意の反復上限のみで停止）

stop_reason — ループの分岐点

役割: Claude API レスポンスに含まれる「なぜモデルが応答を打ち切ったか」を示すフィールド。エージェントループでは次のアクションを決定する唯一信頼できる構造化シグナル。

仕組み: モデルがツールを呼びたい時は "tool_use"、自然に応答完了したときは "end_turn"、トークン上限到達なら "max_tokens" を返す。ループ実装側はこの値を switch で分岐して次の API 呼び出しを組み立てる。

使いどころ: 自律エージェント全般のメインループ制御。Agent SDK でも内部で同じロジックが動いている。

無限再試行（アンチパターン）

役割: 上限なくエラーを再試行し続ける危険な実装パターン。絶対に避けるべき本番アンチパターン。コスト爆発・サービス劣化・連鎖障害を引き起こす。

  • 典型例: 「サービス利用不可」というだけの汎用エラーで全て再試行 → 課金 API なら数分でコストが暴騰する。

  • 避けるべき: 失敗を黙って隠して「完成しました」と言うのは最悪のアンチパターン。下流の意思決定者が誤った確信を持つ。

マルチ懸念リクエストの並列分解

役割: 顧客が 1 つのメッセージに複数の問題を含めた時（「返金 + 配送変更 + 解約理由を聞きたい」）、それぞれを独立して並列調査し、最後に統合解決する設計パターン。

仕組み: マルチ懸念を検出 → 個別の問題に分解 → 共有顧客コンテキスト（本人確認済み情報）を持ったまま並列で各問題を調査 → 統合エージェントが 3 件の結論を 1 つの応答にまとめる。

使いどころ: カスタマーサポートエージェント、ヘルプデスク、複雑な相談業務、複数チケットを束ねた問い合わせ。

  • 失敗パターン: 単純な逐次処理だと「3 件のうち 1 件目だけ解決」で終わりがち。並列分解で全件カバー、統合段階で関連性を検査するのが正解。

Pydantic バリデーション

役割: Python の型ベース検証ライブラリ。tool_use による JSON 構文エラー排除の次段階として、意味的バリデーション（値の整合性・ビジネスルール）を担う。

仕組み: Pydantic モデルにフィールド型・制約・カスタムバリデータを定義 → Claude の出力を Model(**output) で検証 → 失敗時は具体的なエラーメッセージ（「total が行明細合計と一致しません」など）を取得 → そのエラー文を retry-with-error プロンプトに注入してモデルに修正させる。

使いどころ: 構造化データ抽出パイプライン、API レスポンス検証、フォーム入力検証、本番抽出システムの品質ゲート。

  • 分担: tool_use + JSON Schema は構文エラーを排除する、Pydantic は意味エラーを捕まえる。両方使うのが本番品質。
